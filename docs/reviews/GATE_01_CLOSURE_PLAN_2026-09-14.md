# Gate 01 修复收敛与进度提效执行约定

日期：2026-09-14；依据：Owner要求解决多轮返修并提高产品进度效率。当前代码仍为858c20a，Gate仍BLOCKED。本文是本轮修复的验收约定，不是新进度源、代码修复结果或Owner阶段放行；实际状态只记录在12_PROGRESS.md。

## 1. 这几轮为什么反复

主要审查轮次的HIGH数由首轮10项、R2的4项、R3的2项，降至R4的1项；原问题持续关闭，并非所有修复都无效。当前仅H12为HIGH，M03/M04/M06/M07为MEDIUM。

从报告能确认三个不同原因：

1. **同一要求只覆盖部分范围。** H08先后遗漏父行变化和事务并发；M03修了输入/审计异常，限流异常仍在catch之外；M04修了17张表却漏11张。这要求枚举本阶段所有相关对象，不能只选几个通过样例。
2. **测试使用的判断依据不够独立。** H09的列类型和两个ORM读数相等，不能证明数据库真实时刻与应用一致；H12直到用原始SQL epoch对照才暴露。通过数增加不等于缺口自动消失。
3. **修复引入新的边界，审查覆盖也到后轮才补齐。** H11来自新增测试清理；M07来自SQL约束和Schema不同步。实现与Reviewer都需要提前固定同一组验收边界，减少交接后才发现遗漏。

依据：CODEX_REVIEW_GATE_01_REVIEW_2_2026-09-13.md、CODEX_REVIEW_GATE_01_REVIEW_3_2026-09-14.md、CODEX_REVIEW_GATE_01_REVIEW_4_2026-09-14.md。以上是这些记录支持的过程诊断，不把责任归因于模型品牌，也不承诺再修一轮后永久零缺陷。

## 2. 本轮目标与边界

本轮目标是交付一份可独立验收的修复版本：已知反例关闭、同类范围核对、关键回归保留、验收依据与版本对应。目标为下一次提交即可验收；实际PASS仍由运行证据决定。

- 当前修复集合固定为H12、M03、M04、M06、M07；不添加功能、替换技术栈或重构无关模块。
- H08/H11及M01/M02/M05已关闭。其他通过项保留有效回归，只有相关实现/依赖/配置变化、已有证据不足以覆盖变化或出现新反例时重开，写明触发原因。
- D01方案A、48小时邀请、领域时间规则和既定任务顺序不变。
- 新发现的真实CRITICAL/HIGH仍必须阻断；新问题须有位置、可复现证据、影响、原合同依据、与本轮改动的关系。不能为保证收敛而忽略安全/数据问题，也不能把普通改进临时升级成放行条件。

## 3. 开始修复前，先完成失败验证与有限范围盘点

在当前冻结版本的独立可丢弃环境中，复现报告的五项反例。失败来自产品断言才算有效；依赖缺失、端口错误等环境故障单独处理。修复前不失败的测试先核对是否打到原反例，不为造失败改变产品规则。

每项以同一行记录：`问题ID → 原合同/必须成立的行为 → 全部受影响对象 → 修复前失败命令/日志 → 修复提交 → 修复后通过命令/日志 → 遗留范围`。表格放在现有CODEX_REVIEW_HANDOFF的本轮区，实际进度仍写12_PROGRESS；不另建可编辑状态看板。

一次完成以下有限盘点，并记录覆盖清单；不扫描或实现后续Phase业务：

| 范围 | 必须核对的内容 | 完成依据 |
|---|---|---|
| H12当前数据库连接与时间消费者 | Web、Worker、初始化/CLI和测试的连接建立方式；当前实现的邀请/会话等依赖绝对时间的路径 | 原始SQL epoch作独立参考；有效/过期边界、连接复用/多连接、UTC与非UTC默认数据库；如某路径使用不同驱动，记录实际类型与行为 |
| M03现有邀请入口 | 创建、预览、接受、撤销的来源/输入/限流/会话/服务/异常返回 | 给出全部当前入口清单；修复遗漏边界，复用已通过验证；DB失败返回稳定JSON和request_id，无业务部分提交 |
| M04领域ID | 当前Schema全部28张领域主键表；认证四表及辅助表单独解释 | 领域28/28枚举核对并阻断非法ID，正常值通过；存量坏行守卫；不能把手写17表或抽7表作为全覆盖 |
| M06测试迁移辅助器 | 首次、重复调用、目标不存在、完整执行后官方CLI接续 | 首次与重复都不越过目标；不存在目标明确失败；已通过的官方元数据兼容回归保留 |
| M07模型/迁移一致性 | 本轮新增或改变的关系、约束、时间定义与Prisma生成差异 | 官方diff不能意外删除同域复合FK；自定义SQL不能由Schema表达的部分逐条解释并保护，不机械要求所有自定义SQL差异为空 |

H12的UTC连接对照只是已验证的修复方向，不能把“在测试库执行过一次SET”当所有连接已解决。旧数据不得盲目平移8小时；只用合成旧库验证，真实数据处置须有实际来源证据。

## 5. 两层检查，减少重复成本

**开发中：**每次仅跑受影响问题的失败/通过测试和相称的类型检查；只有修改影响或新失败才扩展。将复验反例整理进现有tests结构，便于下次直接运行；不另建庞大测试框架，不以临时手工日志替代长期回归。

**最终候选：**一次运行类型、Unit、完整Integration、build、E2E及本轮需要的正式迁移/运行验证。保留目前18/60/8中的有效行为，不以固定数量为目标或删断言凑绿。每个失败保留首次错误与处理结果，不隐藏不稳定测试。

H12和M04/M07影响共同连接/迁移，本轮需要复验真实容器启动、空库及858c20a旧库升级、重复迁移、坏行守卫；改变连接串时覆盖默认和特殊字符密码。更早历史升级链未改时可引用已冻结证据，解释适用条件，不无理由每次重跑全部旧实验。Reviewer独立执行关键反例和必要回归，不能只复述ZCode日志。

优先复用package.json现有命令与已有隔离运行脚本。可以加一个很薄的本地验证入口，串行执行并汇总真实退出码；只有能减少手工步骤时才加，不建设新CI平台或操作其他数据库。

## 6. 固定关闭与放行标准

- ZCode关闭一项：修复前能复现、修复后反例不成立、同类范围核对完成、有效回归通过，证据对应同一候选代码。
- Codex结束复审：逐项复核五项处理、检查本轮差异及受影响边界；已通过问题无触发原因不反复重开。真实新HIGH仍列入，不约定“为了进度必须PASS”。
- Gate通过至少要求没有未关闭CRITICAL/HIGH，当前TASK合同验收满足、必要证据完整。MEDIUM保持原等级与已核定期限；本轮争取一并补齐。如确有合理延期理由，必须明确残余风险、责任TASK、最晚触发点和Reviewer核定，不能把“未处理”自动变成HIGH，也不能擅自认定延期已获批准。
- 本轮已到期限的M04、下一次Schema变更前的M07随此次TASK-002处理；M03/M06沿R4最小范围补完。期限变更须说明依据，不能复制旧延期句式。
- 技术PASS与Owner阶段放行分开。Owner只处理产品裁决、范围变化与阶段放行，不负责翻译逐条技术缺陷。

## 7. 产品进度怎样看得见

保留8个Phase与原TASK依赖。阶段内按既定授权连续做，一次一个TASK；阶段结束才交Gate。以下是进度汇报口径，不是提前启动授权：

| 已有阶段 | 给Owner看的实际结果 |
|---|---|
| Phase1结束 | 能可靠登录/邀请，组织与角色隔离正确，运行及迁移可复现；还不能声称产品业务闭环完成 |
| Phase2结束 | 店铺/数据源、统一数据格式与上传任务基础可验证 |
| Phase3结束 | 六类CSV能按规则校验、确认、入库、去重与恢复；尚不等于老板看板可用 |
| Phase4结束 | 经营指标与异常能用黄金样本人工核对 |
| Phase5–6结束 | 有证据的AI结果和老板3分钟阅读路径可演示 |
| Phase7–8结束 | 完整工作台、试点运维与真实试用验收按合同完成 |

每次汇报只突出：本次新增可验证能力、当前未关闭阻塞、下一步可交付结果、是否需要Owner决策。TASK数量/测试数量只是证据，不能作为产品完成百分比。

后续每个TASK沿09_TASKS已有规定，在实现前写出关键失败用例与验收依据；高依赖边界采用短契约检查，避免到阶段末才发现基础假设不成立。不要把每个TASK都增加一次正式Gate。Owner可同时整理已有脱敏样本和人工期望结果作为后续输入；本轮不提前实施TASK-005/006或处理真实客户数据。

范围对速度的影响需单独说明：当前P0含30个TASK、六类CSV与八个阶段，不能把完整交付等同很小的首试版本。如果Owner更优先尽早获得首个商家试用反馈，建议之后单独裁决“首试最小闭环与可后置能力”，依据具体商家数据和使用场景裁剪。该建议尚未获产品范围批准，本轮不删功能、不调整任务顺序，也不降低身份、数据隔离和金额正确性要求；它不阻塞当前Gate修复。

若下一轮相同反例仍未关闭，应停止重复局部补丁，先针对该行为复核根因与失败证据；是否更换主开发/独立Reviewer由Owner明确决定。当前保持ZCode主开发、Codex独立审查；不承诺工具间自动传话或后台同步。
