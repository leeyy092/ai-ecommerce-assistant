# 产品定位与范围

版本：v1.0 · 2026-09-11。状态：产品与工程规格；应用尚未开发。P0为本次定义的开发范围，P1/P2只作规划。

# PART 1｜产品定位

## 1.1 目标用户

产品面向约 10～100 人的国内电商及跨境电商团队。首轮试点选择能导出商品、订单和客服文件，且有负责人愿意每天核对结论的企业。团队规模是招募画像，不作为权限人数限制；当前没有真实付费证据，以下付费动机均为待访谈和试用验证的假设。

| 用户 | 日常工作 | 最大痛点 | 最关心的数据 | 使用理由 | 可能愿意付费的理由与验证 |
|---|---|---|---|---|---|
| 电商老板 | 看经营、分配资源、决定优先事项 | 报表分散，发现问题后还需追问发生在哪个商品 | GMV、订单、退款、广告花费、异常影响范围 | 一页看到有依据的问题及当天最先处理的事 | 如果能减少反复找人核数，并更早发现重要问题；记录实际查看次数、决策案例和报价接受情况 |
| 运营负责人 | 汇总日报、复盘活动、检查投放、协调商品客服 | 整理数字耗时，部门口径不一致 | 销量变化、SKU 排名、广告 ROAS、退款与投诉趋势 | 自动整理同口径日报，回看建议是否处理 | 如果能替代重复汇总并减少漏查；对比人工耗时并观察第二次主动使用 |
| 商品运营 | 跟踪 SKU、分析表现、核对退货与商品反馈 | 总销量掩盖单品问题，客户反馈难对应商品 | SKU 销量/销售额、成熟队列退款率、关联 VOC | 从下滑商品直接查看订单统计和脱敏反馈证据 | 如果能稳定找出值得复核的商品；验证是否据此完成一次商品调整 |
| 客服负责人 | 整理 FAQ、归纳投诉、核查售后、反馈商品问题 | 大量聊天缺少一致分类，新增问题靠印象发现 | 高频问法、投诉主题、售后原因、负面反馈趋势 | 只看本岗位需要的客服证据，修正标签并记录处理 | 如果能减少手工分类并形成可用反馈；对照标注质量、时间及实际付费，不能用点赞代替 |

## 1.2 核心价值

系统先把各来源文件变成口径明确的经营事实，再用规则发现需要复核的变化，最后把事实、客户原话与建议放在一起。老板无需自己拼接日报，就能知道哪个 SKU 下滑、哪类售后上升、广告花费是否超出历史范围，以及先检查什么。

首版交付的是可追溯的经营晨报。系统能指出“哪些记录支持判断”，不能证明促销、质量或投放是销量变化的因果，也不承诺提高销售额。真实价值通过试点记录验证：首次得到可核对晨报的时间、原人工日报耗时、真实再次使用、接受并执行的建议、报价接受与付款分别记录。

## 1.3 MVP 的三个核心价值

1. **每日少做一次手工拼报表。** 导入后得到同店铺、同币种、同时间口径的指标和摘要；缺数据明确显示，不用编造零值补齐。
2. **把需要先查的问题集中呈现。** 规则标出异常 SKU、退款、广告及客服变化，并给出基准、样本量和来源，用户能直接复核。
3. **把反馈变成当天能执行的行动。** 聚合 FAQ/VOC 后提供有证据、标明假设和优先级的建议，用户可采纳、完成或忽略，保留历史版本。

## 1.4 MVP 边界

V1/P0 实现一个完整闭环：登录及组织固定角色 → 建店 → 导入 6 类 CSV → 确定性指标 → 规则异常 → 客服文本分类聚合 → 日报与建议 → 人工记录处理状态。首页、SKU 对照、客服分析、异常和日报共用这套事实，不重复建设 BI。每次只查看一家店；Mock 与真实文件通过同一 Adapter 契约，演示数据在独立演示组织中明确标记。

V1 暂不做以下功能；展示“数据不足”不等于已经实现这些能力：

| 暂不做 | 后续阶段/原因 |
|---|---|
| 平台/ERP 自动同步 | P1 逐个平台验证授权与字段后接入 |
| 原生 XLSX、多工作表与 .xls/.xlsm | XLSX P1；V1 仅 CSV UTF-8，Excel 需另存 |
| 跨店铺合并经营与币种换算 | P1，需要统一汇率和合并口径 |
| 自定义 RBAC、店铺级权限、Owner 转移 | P1，先用固定角色 |
| 独立产品分析工作台 | P1，P0 只在 SKU 页做产品聚合 |
| 企业知识库和 RAG 回复建议 | P1，需要知识审核与检索验证 |
| 利润/经营 ROI 分析 | P1，需要完整成本账；P0 只展示不可计算说明 |
| 实时库存、库存周转、补货预测 | P1，需要库存与采购流水 |
| 竞品实时抓取及监控 | P2，需要合法可用来源与持续采集 |
| 自动卖点生成和多平台内容发布 | 卖点/草稿 P1；发布 P2，需商品事实约束和人工审核 |
| 自动客服发信或回复 | P2，不能由首版建议自动触发 |
| 广告预算调整、自动调价、选品 Agent | P2，需要外部执行权限、限额和回滚 |
| 自定义报表/指标/告警 DSL | P1，P0 仅固定指标和有边界的规则阈值 |
| 多人任务分派、审批流与项目管理 | P1，P0 只记录当前用户的行动状态 |
| 业务原始行在线编辑、批量删除 | P1；P0 更正后重导，替换同一业务键，不累加 |
| 公开自助注册、支付订阅、短信邮件自动邀请 | P1，试点由部署初始化 Owner，管理员复制邀请链接 |

## 1.5 真实试点与付费验证

首轮先找能给出至少28天脱敏导出、SKU身份稳定、愿意核对日报的一两家厦门企业。国内与跨境均可，但每次试点只选一个店铺、一种记账币种和一位业务负责人。优先有每周重复整理日报/汇总客服问题的真实事件；10—100人只是筛选线索，不是证明有购买需求。

先记录最近一次日报或问题排查：谁做、用了哪些文件、耗时多久、哪里错过或重复核数、是否已有付费工具。将原流程工时、AI工具工时、发现但无价值的异常、错误建议、真实采用动作分列。试用7个工作日，至少核对3次晨报与一次真实经营事件；这只是试点安排建议，不是已发生的客户成果。

试点结束分别记录：是否实际导入、是否第二次主动打开、是否采用动作、是否接受具体报价、是否实际付款。没有问题、数据拿不到、已有替代方案足够、拒绝披露都保留为不同负面样本。不能把“愿意试试”写成购买。先确定固定试点范围、接入工时和交付报价，再根据复用与支持成本决定后续订阅价格；本规格不假定客户会支付某个价位。

首次演示使用合成数据：说明数据日期和演示标识→打开一个真实可复核的异常→回到具体SKU/脱敏消息证据→记录本人下一步→关闭模型后展示指标仍可用。演示功能通过并不等于真实客户愿意付费。


# PART 19｜开发优先级

阶段优先级只表示开发范围，与 AI 建议中的行动紧急度分开管理；页面可通过 Tab 合并，不能按 18 个模块拆成 18 套独立系统。

| 阶段 | 交付范围 | 明确完成边界 | 进入下一阶段依据 |
|---|---|---|---|
| P0 | 身份/组织/固定角色与店铺；6 类 CSV 导入和覆盖；确定性指标与规则；SKU 列表/详情；FAQ/VOC/售后聚合；首页、日报、建议与本人状态；必要设置/审计/失败恢复 | 一个店铺从文件到晨报可完整走通；金额/时间/退款口径一致；CS/跨租户权限验证；AI 失败页面仍可用；PART 21/22 验收通过 | 真实企业能自行导入、复核并再次使用；记录发现问题/实际动作/报价/付款，分开判断 |
| P1 | 已验证平台 Connector；XLSX；独立产品分析；完整成本 ROI；库存/周转；RAG 知识库和回复草稿；卖点/内容草稿；自定义角色/店铺权限；VOC 周报；成本和多人行动需求 | 每项需单独 TASK、数据契约、权限与测试；存在明确用户需求后逐项排期 | 有真实使用频率和可获取数据，能说明收费或续用价值，不能因竞品拥有就自动加入 |
| P2 | 竞品监控；广告/调价/选品 Agent；自动客服和发布；外部任务执行与审批回滚 | 可用外部授权、执行限额、人工审批、幂等/撤销/审计和安全验收齐备 | 先证明建议可用，再验证执行可靠性；不能将首版的手工状态当成已实现自动化 |

P0 建议依赖顺序：身份与权限 → 数据契约/模板 → 文件校验与原子提交 → 指标和覆盖 → 异常 → VOC → AI 校验/日报 → 页面联调 → 全流程验收。任务拆分见 PART 20，不能因“首页需要所有区域”提前开发 P1/P2；缺少成本、库存或竞品数据时保留清晰说明，不模拟结果。

P0 演示需能从独立 Mock 组织完整重现，再让真实企业上传一组脱敏文件。演示通过、本地测试通过、线上部署完成、客户再次使用、实际付款是不同状态；本次仅交付规格，所有应用开发任务初始为 TODO。


# PART 25｜未来扩展设计

以下只预留边界，不创建P0页面、不申请平台权限、不安装Agent框架。

| 未来能力 | 当前必须预留 | 接入时要额外证明 | 阶段 |
|---|---|---|---|
| Amazon API | DataSource provider/namespace、Connector游标与授权引用、原始事件ID、退货退款映射 | 实际企业授权、可读范围、历史窗口、限流、归因定义与当前标准口径差异 | P1 |
| Shopify API | 同一NormalizedBatch、UTC事件与店铺币种、Webhook事件幂等键 | 店铺权限、订单行/退款字段映射、删除和补拉语义、重复Webhook处理 | P1 |
| Shopee API | 区域/站点作为source维度、分页与重试checkpoint | 授权区域、访问范围、接口稳定性，不能按平台名推断已接通 | P1 |
| TikTok Shop API | 商家账号/店铺外部ID、订单与退款分层 | 真实账号权限与事件语义、区域差异、流量/广告归因是否可获取 | P1 |
| ERP | source_namespace、SKU别名、分页批次、源更新时间 | 是否能稳定导出/调用；订单、库存、成本分别对应哪套事实 | P1 |
| 客服系统 | message/conversation匿名ID、原始语言、脱敏adapter | 可读会话范围与平台许可，消息是否完整、是否有人工回复样本 | P1 |
| 自动客服 | 只读建议接口和审核/执行接口分离；Policy/Knowledge版本 | FAQ知识、RAG引用、转人工路径、低风险评测和实际消息发送授权 | P2 |
| 广告优化Agent | Recommendation与ExecutionCommand独立，执行审计、预算边界 | 沙盒效果、明确授权、幂等执行、限额、停止机制、真实归因评估 | P2 |
| 自动调价 | 价格快照、上下限、版本锁、审批后命令ID | 最低毛利约束、库存/成本准确、平台写入权限、回滚能力 | P2 |
| 选品Agent | 独立研究证据/数据许可层，不污染现有经营事实 | 市场数据可用性、历史回测、人工研究价值与采购/经营证据 | P2 |
| 竞品监控 | Competitor及Observation概念预留，来源/采集时间/事实链接 | 合法可访问来源、同款身份、促销与常态价区分、变动去重 | P2 |
| 自动执行运营任务 | ActionState与ExecutionAttempt分离，权限scope、dry_run和审计 | 逐类动作获授权、失败重试不会重复副作用、可取消/补偿 | P2 |
| 多币种/多店总览 | 每个金额保留币种与日期、FXRate版本概念 | 明确汇率来源与兑换日，集团去重、税费定义、跨币种报告可复算 | P1 |
| 成本ROI/库存周转 | 成本账、库存快照/流水、归属期间与coverage概念 | 足够成本来源、退货可售价值、平均库存口径，不能以库存单点代替周转 | P1 |

只读 Connector 的最低协议包括：能力声明、配置校验、按时间窗拉取、标准化、checkpoint、错误分类、同步结果。`checkpoint` 只能在标准数据提交成功后推进；失败从安全位置重拉，仍使用与CSV相同自然键和更新规则。平台接口权限及字段尚未实测，不能因为这里有Adapter就声称已支持真实连接。

所有未来写入操作必须走新的执行边界，保留 `requested_by / approved_by / action_type / idempotency_key / limits / executed_at / external_receipt / compensation_status`。P0的“完成行动”只是用户记录，绝不解释为已在平台执行。
